# content-api Specification

## Purpose

Даёт интерфейсу справочника и будущим серверным возможностям (генерация примеров, закрепление) единый доступ на чтение к проверенному контенту по HTTP.

## Requirements

### Requirement: Список тем в порядке учебного маршрута
Запрос `GET /api/topics` MUST возвращать все темы в порядке учебного маршрута. Для каждой темы ответ MUST содержать идентификатор, название, уровень, идентификатор раздела, суть и признак заглушки.

#### Scenario: Порядок совпадает с маршрутом
- **WHEN** клиент запрашивает `GET /api/topics`
- **THEN** темы в ответе идут в том же порядке, что и в учебном маршруте

#### Scenario: Заглушка помечена
- **WHEN** в справочнике есть тема без статьи
- **THEN** в ответе `GET /api/topics` у этой темы признак заглушки установлен, а у написанных тем — нет

### Requirement: Список разделов
Запрос `GET /api/sections` MUST возвращать все разделы в порядке, заданном в контенте, с идентификатором и названием каждого.

#### Scenario: Разделы в заданном порядке
- **WHEN** клиент запрашивает `GET /api/sections`
- **THEN** ответ содержит все разделы в том порядке, в котором они перечислены в контенте

### Requirement: Тема целиком
Запрос `GET /api/topics/{id}` MUST возвращать метаданные темы, название её раздела, блоки статьи в порядке шаблона, примеры, пререквизиты и связанные темы. Каждый блок MUST содержать свой вид и текст в формате Markdown.

#### Scenario: Написанная тема
- **WHEN** клиент запрашивает тему, у которой есть блоки «Формула» и «Формы» и три примера
- **THEN** ответ содержит два блока в этом порядке, каждый со своим видом и текстом, и три примера

#### Scenario: Заглушка
- **WHEN** клиент запрашивает тему-заглушку
- **THEN** ответ содержит метаданные темы, пустой список блоков и установленный признак заглушки

### Requirement: Ссылки на темы самодостаточны
Каждая ссылка на тему в ответе о теме — пререквизит, связанная тема, предыдущая или следующая тема — MUST содержать идентификатор, название и признак заглушки, чтобы клиенту не требовались дополнительные запросы.

#### Scenario: Пререквизит с названием
- **WHEN** клиент запрашивает тему, у которой пререквизит — тема «Гармония гласных»
- **THEN** в списке пререквизитов есть элемент с идентификатором этой темы, названием «Гармония гласных» и признаком заглушки

### Requirement: Соседи по учебному маршруту
Ответ о теме MUST содержать ссылки на предыдущую и следующую темы учебного маршрута. У первой темы маршрута предыдущая тема MUST отсутствовать, у последней — следующая.

#### Scenario: Тема в середине маршрута
- **WHEN** клиент запрашивает тему, стоящую в маршруте между двумя другими
- **THEN** ответ содержит ссылки на обе соседние темы

#### Scenario: Первая тема маршрута
- **WHEN** клиент запрашивает первую тему маршрута
- **THEN** предыдущая тема в ответе отсутствует, а следующая есть

### Requirement: Пример в ответе
Каждый пример в ответе о теме MUST содержать турецкий текст и перевод без служебной разметки, сведения о выделенных фрагментах, источник и, если заданы, примечание и разбор. Разбор MUST быть структурирован по словам и морфемам: у каждой морфемы есть её форма и значение. Значение морфемы MUST быть также разложено на части, и каждая часть MUST быть помечена как обозначение или как лексическое значение, чтобы клиенту не приходилось определять это самому.

#### Scenario: Пример с разбором
- **WHEN** у примера в контенте `morphemes: ev-ler-im-de` и `gloss: дом-МН-1ЕД.ПРИТ-МЕСТ`
- **THEN** в ответе разбор состоит из одного слова с четырьмя морфемами, у первой форма `ev` и значение `дом`, у последней форма `de` и значение `МЕСТ`

#### Scenario: Части значения помечены
- **WHEN** у примера в контенте `morphemes: ev-ler-im-de` и `gloss: дом-МН-1ЕД.ПРИТ-МЕСТ`
- **THEN** в ответе у морфемы `ev` одна часть значения `дом`, помеченная как лексическое значение, а у морфемы `im` две части `1ЕД` и `ПРИТ`, обе помеченные как обозначения

#### Scenario: Пример без разбора
- **WHEN** у примера в контенте нет разбора
- **THEN** в ответе у этого примера разбор отсутствует

#### Scenario: Пример с выделением
- **WHEN** у примера в контенте `tr: Ev*de*yim.`
- **THEN** в ответе турецкий текст равен `Evdeyim.`, и отдельно указано, что выделен фрагмент `de`

### Requirement: Неизвестная тема
Запрос темы с идентификатором, которого нет в справочнике, MUST возвращать ответ со статусом 404 и машиночитаемым описанием ошибки.

#### Scenario: Темы не существует
- **WHEN** клиент запрашивает `GET /api/topics/no-such-topic`
- **THEN** сервер отвечает статусом 404 и телом в формате JSON с описанием ошибки

### Requirement: Обозначения
Запрос `GET /api/notation` MUST возвращать вводный текст в формате Markdown и список обозначений в порядке, заданном в контенте, с кодом и расшифровкой каждого.

#### Scenario: Список обозначений
- **WHEN** клиент запрашивает `GET /api/notation`
- **THEN** ответ содержит вводный текст и все обозначения в порядке их перечисления в контенте

### Requirement: API только для чтения
API MUST NOT предоставлять операций, изменяющих контент. Запрос с изменяющим методом к существующему адресу MUST отклоняться.

#### Scenario: Попытка изменения
- **WHEN** клиент отправляет `POST /api/topics`
- **THEN** сервер отвечает статусом 405 и не изменяет контент

### Requirement: Машиночитаемое описание контракта
Сервер MUST публиковать по адресу `GET /api/openapi.json` описание API в формате OpenAPI, которое покрывает все операции и схемы их ответов.

#### Scenario: Описание доступно
- **WHEN** клиент запрашивает `GET /api/openapi.json`
- **THEN** ответ содержит документ OpenAPI с операциями `/api/topics`, `/api/topics/{id}`, `/api/sections` и `/api/notation` и схемами их ответов
