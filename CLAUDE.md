# Турецкий грамматический справочник

Говори о предметной области словами из [GLOSSARY.md](GLOSSARY.md): в коде, в текстах интерфейса и в контенте. У каждого термина там указаны синонимы, которые в проекте заменяем этим термином.

## Где смотреть

- [GLOSSARY.md](GLOSSARY.md): прочитай, прежде чем давать имя чему-либо (идентификатор, поле API, текст интерфейса, сообщение проверки).
- [ARCHITECTURE.md](ARCHITECTURE.md): прочитай, прежде чем добавлять модуль, менять порядок загрузки и проверки контента или API. Новый модуль получает строку в карте кода.
- [content/README.md](content/README.md): прочитай, прежде чем писать или править файлы в `content/`. Там формат файлов, шаблон статьи, правила разбора по морфемам и правила карты тем.
- `openspec/specs/`: контракты поведения. Изменение поведения идёт через `/opsx:propose` → `/opsx:apply` → `/opsx:archive`; так же идёт рефакторинг, которому нужен план, с `skip_specs: true` в его `.openspec.yaml`. Исправление, которое не меняет поведения, идёт сразу в код.
- [README.md](README.md): установка, запуск и задачи mise.

## Проверка

- `mise run check` — линтеры, типы, слои, тесты, проверка контента и аудит зависимостей; то же запускает CI. Работа готова, когда эта команда проходит.
- `mise run content:check` — только проверка контента; печатает все ошибки с файлом и причиной.
- `mise run content:words` — проверка словоформ: печатает турецкие слова контента, которых не признаёт морфологический анализатор, и файл каждого. Входит в `check`.
- `mise run content:stats` — сводка наполнения: сколько тем написано на каждом уровне и сколько примеров у каждой написанной темы.
- `mise run format` — исправляет форматирование.
- Остальные задачи показывает `mise tasks`.
- Один тест: `mise exec -- uv run --directory backend pytest tests/content/test_gloss.py -k <имя>`, `mise exec -- pnpm --dir frontend exec vitest --run src/components/ExampleCard.test.tsx`.
- Зависимости: `mise exec -- uv add --directory backend [--dev] <пакет>`, `mise exec -- pnpm --dir frontend add [-D] <пакет>`; точные версии — в `uv.lock` и `pnpm-lock.yaml`.

Запускай инструменты через `mise run` или `mise exec --`: так берутся версии из `mise.toml`, а не из окружения оболочки.

`hk.pkl` — единственный список проверок: из него берут шаги хуки git (pre-commit — быстрые, pre-push — с тестами, commit-msg — сообщение коммита) и задачи `check`, `lint`, `format`. Новая проверка добавляется туда. Хуки ставит `mise run setup`.

## Правила

- Слои сервера сверху вниз: `cli` → `api` | `wordforms` → `content` → `settings`, импорты только вниз; `api` и `wordforms` друг друга не импортируют. Это проверяет `lint-imports` по контракту в `backend/pyproject.toml`; новый подпакет добавляется в контракт.
- Новый модуль получает докстринг, который называет его роль не длиннее чем в трёх строках, и строку в карте кода ARCHITECTURE.md; подробности — там или в спецификации. Оба условия проверяет `backend/tests/test_architecture.py`.
- Типы строгие. Python: mypy `strict` и сверх него `disallow_any_explicit` — `Any` не пишется нигде; у библиотеки без аннотаций (zeyrek) на границе стоит `Protocol`. TypeScript: `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` и typescript-eslint `strictTypeChecked` — без `any`, без `!` для отказа от `null`, без `@ts-ignore`. `type: ignore` и `eslint-disable` не ставятся: если проверка мешает, правится код или правило в конфиге с комментарием, почему.
- `object` (Python) и `unknown` (TypeScript) — только для данных, форма которых ещё не проверена: сырой YAML до модели из `content.files`, ответ до разбора. Для значения с известной формой — dataclass, Pydantic-модель или тип из `schema.d.ts`.
- Неиспользуемого кода не остаётся: ruff ловит неиспользуемые аргументы и закомментированный код, knip — неиспользуемые файлы, экспорты и зависимости интерфейса. Экспортируется только то, что импортируют другие модули.
- `frontend/src/api/schema.d.ts` генерируется `mise run gen:api` и руками не правится; после изменения схем ответов API его перегенерируют и коммитят.
- CI на GitHub запускает `mise run check`, проверяет сообщения коммитов и падает, если после проверок в дереве что-то изменилось.

## Коммиты

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/): `<type>(<scope>)?: <description>`. Тип — по-английски, описание — по-русски, со строчной буквы, без точки в конце, заголовок не длиннее 100 символов. Дальше пустая строка, тело — *зачем* сделано изменение, и футеры. Хук commit-msg сверяет типы и scope с `commitlint.config.js`; ставит его `mise run setup`.

Тип:

- `feat` — то, что видит читатель: новая тема или статья, страница, поле API, команда, новая проверка контента. `fix` — исправление ошибки, в том числе в контенте (неверная форма, перевод, разбор).
- `refactor` / `perf` — поведение не меняется; `test` — только тесты.
- `docs` — README, CLAUDE.md, ARCHITECTURE.md, GLOSSARY.md, `content/README.md`, `docs/`, спецификации и архивы OpenSpec (`docs(openspec): …`).
- `build` — зависимости и инструменты: `mise.toml`, `pyproject.toml`, `uv.lock`, `package.json`, `pnpm-lock.yaml`, `hk.pkl`, `commitlint.config.js`, CI (`.github/`).
- `chore` — остальное, что не код.
- Изменение формата файлов контента, которое старые файлы не проходят: `!` после scope и футер `BREAKING CHANGE:`.

Scope — часть проекта: `content` (файлы `content/`), `loader` (пакет `content`: модель, загрузка, проверка), `words` (проверка словоформ), `api`, `ui` (интерфейс), `cli`, `openspec`. Изменение нескольких частей пишется без scope.

```
feat(content): тема «Местный падеж -DA» вместо заглушки
fix(content): разбор gidiyorum в примерах настоящего времени
feat(loader)!: обязательное поле summary в метаданных темы
docs(openspec): архив изменения write-a1-topics
```
